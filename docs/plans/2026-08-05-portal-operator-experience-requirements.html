Portal Operator Experience - Requirements

Portal should become the place where one human can see what agents need, steer the exact session, and judge a release from one evidence-backed surface. The immediate defect is comments that appear sent but remain waiting forever; the larger opportunity is an operator console rather than a collection of unrelated object pages.

Goal Capsule

Give the operator one reliable loop: notice work that needs attention, address the exact agent without leaving Portal, and inspect a release whose build, capture, preview, source, and distribution state agree.

Product Contract

A1.

Operator

Sees every live agent and pending decision, steers one exact session, and remains the accountable owner.

A2.

Agent session

Receives ordered steering while working and exposes enough identity and state to avoid sending text to a neighboring pane.

A3.

Release steward

Assembles a versioned evidence bundle and publishes it only after deterministic readiness checks pass.

A4.

Reviewer

Uses Portal to watch gameplay, try the browser build, download the artifact, compare provenance, and leave contextual feedback.

Core flows

F1.

Notice

Portal surfaces live sessions, unread changes, and items that need the operator.

→
F2.

Steer

The operator selects a stable session identity, sends a comment, and sees delivered or retained-for-retry.

→
F3.

Prove

The release steward binds source, artifact, device or simulator capture, poster, playable preview, and changelog.

→
F4.

Judge

The reviewer experiences the exact published release and can distinguish Portal publication from store availability.

Product Requirements

Agent conversation and delivery

IDRequirementWhy it matters
R1.Portal must expose a primary Agents tab listing live sessions with provider, project, task, state, and stable session identity.Display labels and pane positions are not identities.
R2.A comment addressed to a live agent must be sent to that exact stable session and report a truthful delivered or failed result.“Queued” cannot mean “perhaps something will poll eventually.”
R3.A failed delivery must preserve the original comment, target, failure reason, attempt history, and retry action without creating a duplicate.Failure should be recoverable and auditable.
R4.Stream notes and answers must offer explicit live-agent targeting while preserving the existing pull queue for headless consumers.Interactive steering and durable polling are separate valid paths.
R5.Agent controls must work across supported Fleet providers and must degrade visibly when a session lacks a live tmux target.Provider parity is part of Portal’s role as a control surface.
R6.Comment text and credentials must never enter command arguments, query strings, access logs, or rendered agent metadata.Portal currently holds sensitive operator context.

Release cockpit

IDRequirementWhy it matters
R7.Every game release must bind a unique version to source revision, artifact digest, factual changelog, gameplay capture, poster, and optional playable web bundle.A page is useful only when its evidence agrees.
R8.Marble Run and Find the Bird must use the same release contract and Portal capabilities, with game-specific build recipes expressed as inputs rather than bespoke Portal code.The workflow should scale to the next game.
R9.Publication must verify the live page, downloads, media playback, browser preview, and local-to-hosted digests after upload.API acceptance is not user-visible proof.
R10.Portal must distinguish internal publication, native-device verification, TestFlight processing, tester availability, and store release.These gates are independent and change asynchronously.
R11.An incomplete game may appear as a draft release workspace only if missing evidence is explicit and no public-release claim is made.This creates an honest Find the Bird entry before all external gates are available.

Operator UX

IDRequirementWhy it matters
R12.The home surface must prioritize “needs you,” failed delivery, unread agent activity, and release blockers over object-type navigation.The operator’s scarce resource is attention.
R13.Activity must be filterable by project, agent, status, and release while retaining durable deep links.One global chronology becomes noise quickly.
R14.Agent reply and release review actions must remain usable on a phone without exposing destructive controls by default.Quick steering is often mobile; release mutation is not.
R15.Contextual feedback should carry the release version, route, viewport, and device context it refers to.Feedback attached to “latest” becomes ambiguous after the next build.

Scope Boundaries

Build now

Exact-session delivery, honest retry state, Agents navigation, formal release skill, and a Find the Bird release attempt against the existing Portal contract.

Blue-sky next

Needs-you home, unread chat tabs, draft release workspaces, evidence annotations, release comparisons, and notification routing.

Outside this run

Autonomous store submissions, production deploys, merges to main, paid services, and replacing Agency Fleet with Portal-owned process discovery.

Cardinal rule

Reuse Agency Fleet as the session authority. Portal stores human intent and delivery evidence; it does not invent another agent registry.

Appendix

Product signals

  • Linear Agent demonstrates persistent agent chats, parallel tabs, unread/working state, and in-context comments.
  • GitHub Copilot steering treats input during work as ordered steering rather than a separate silent queue.
  • Vercel comments attach feedback to the actual preview surface and preserve thread activity.
  • App Store Connect build metadata keeps processing, warnings, version, and build identity visible as separate release facts.

Repository anchors

  • gallery/server.py — Portal routes and web authentication.
  • gallery/db.py — append-only messages and versioned game records.
  • src/agency/fleet/tmux.py — stable tmux pane resolution and literal reply transport.
  • src/agency/fleet/hud.py — Fleet session inventory and JSON snapshot.
