Goal Capsule

When the operator comments in Portal, the exact chosen live agent receives ordered terminal input or Portal preserves a diagnosable retryable record. When a game appears in Portal, the page proves which source produced which artifact and matching media, while store and tester availability remain separate gates.

Product Contract

Scope decision

The first Agents tab is outbound steering plus durable delivery history, not terminal transcript ingestion. Calling it fully bidirectional chat before an agent-response protocol exists would be decorative dishonesty.

Planning Contract

High-Level Design

Agency remains authoritative for live session identity. Portal stores the human message and an append-only attempt ledger. A targeted message is excluded from the generic pull queue, claimed synchronously for submission, and consumed by transport only after Agency confirms that both literal text and Enter reached the same stable pane. This does not prove the agent has read or acted on it.

Key Technical Decisions

KTD1.

Reuse Fleet; do not mirror it

Portal invokes a small Agency JSON surface at request time. The DTO contains provider, SID, display label, project, task, state, freshness, and replyability only.

KTD2.

Model delivery separately from message content

Portal schema v12 adds target/current delivery fields plus append-only delivery attempts. Generic pull excludes explicitly targeted messages, preventing a background poller from consuming someone else’s comment.

KTD3.

Single-paragraph literal input in v1

The Agency primitive rejects line breaks, NUL, control characters, blank input, and oversized payloads. This avoids terminal submission ambiguity until bracketed-paste transport is implemented and tested.

KTD4.

Three outcomes, not a boolean fiction

If literal text fails, the attempt is failed. If text succeeds but Enter fails, the outcome is unknown and is never automatically retried. Only two successful tmux calls produce submitted-to-terminal; agent acknowledgement remains future work.

KTD5.

One reusable release contract

The Agency skill carries global policy and delegates game-specific build commands to each game. Portal remains game-agnostic and Store/TestFlight mutations remain separately authorized.

Acceptance Examples

AE1.

Given two Fleet sessions and panes have moved, when the operator addresses provider and SID B, only B receives the comment and Portal records submitted to terminal.

AE2.

Given text reaches the pane but Enter fails, Portal records submission unknown, leaves the message unconsumed, and does not offer automatic retry.

AE3.

Given Agency is unavailable, the Agents tab loads with a diagnosable state and the operator’s failed comment remains visible for later retry.

AE4.

Given FTB lacks a fresh matching native artifact or capture, no public release is created and the report names the exact missing gate.

Definition of Done

  1. Agency exact-session reply tests and disposable tmux integration pass.
  2. Portal tests pass, and targeted stream comments no longer remain silently queued.
  3. The Agents tab and stream targeting are inspected at desktop and phone sizes.
  4. The always-on release skill validates, indexes, and syncs in a temporary home.
  5. Marble Run is documented from live evidence; Find the Bird is either live with matching evidence or explicitly blocked without a false release record.
  6. CE review findings are resolved or reported, and the compound/UX artifacts are grounded and visually inspected.

Appendix

Risks and Dependencies

Risk · controlled

Terminal partial delivery

Two tmux calls can partially succeed; structured ambiguous state and no automatic retry contain duplication.

Risk · controlled

Fleet inventory sensitivity

Portal sanitizes Agency output and never renders pane, TTY, PID, transcript, raw path, or prompt fields.

External dependency

Find the Bird capture lane

The registered iPhone is currently unavailable and no Android device is attached. Publication depends on a fresh coherent artifact/capture pair, not on Portal code.

Boundary

External release authority

No production deploy, merge to main, TestFlight upload, tester change, review submission, or store release occurs without its separate authorization.
